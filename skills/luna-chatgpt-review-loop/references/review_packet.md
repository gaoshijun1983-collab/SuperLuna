# 每轮评审包

每轮提交前按本页组织材料。目标是让 Chat 在明确边界内独立审查，而不是复述实施任务的结论。

本页“提交”只表示把审阅包单次发送给固定 Chat，不等于执行 `git commit` 或 `git push`。默认
直接使用经过验证的工作树 diff、文件内容和测试输出作为证据。用户未明确要求 Git 提交时，不得
把创建 commit、写入外部 Git worktree 元数据、权限审批或推送设为进入评审的前置条件；Git
索引不可写只需在证据边界中标明“未创建 commit”，不能阻断已经可读、可测试的本地改进。若
项目自身的验收合同明确要求 commit identity，则按真实阻塞处理，不可伪造。

每份正式审阅包必须以控制器 `render-review-run-binding` 的完整输出开头。该区块把本次 state、
Controller/Skill 版本、实施任务、固定 Chat 和 state-local 轮次绑定在一起。复用旧 Chat 时，历史
里的其他运行身份只能作为背景；Reviewer 不得用旧身份改名、计数或拒绝当前区块已绑定的新运行。
缺少区块或区块与发送授权不一致时不得发送。

控制器输出的起止标记必须原样保留：

```text
[SUPERLUNA_REVIEW_RUN]
...
[/SUPERLUNA_REVIEW_RUN]
```

## 适当范围

- 一轮只审一个可决策问题，不把整个项目塞进日常评审。
- 给出 2–4 个明确审查问题；每个问题都必须能由本轮证据回答。
- 决策问题只能依赖提交前已经发生并记录的事实；未来计划不能作为 PASS 证据。需要等待
  occurrence、回复身份或消费后状态才能证明的结论，应在这些动作完成后的下一份评审包中审查。
- 评审证据截止点是本次请求提交时。本次回复产生后才能执行的回复登记、账户名额释放、等待任务
  删除和状态续接由控制器在回复后验证，不得成为本次 verdict 的 PASS 前置条件；已完成的前轮
  收尾可以进入下一轮证据。
- 保留硬边界，但允许 Chat 指出一个足以推翻本轮结论的范围外 blocker。
- 下一步只保留一个主行动，并附完成条件和最小验证；不得只写“继续优化”。

范围按风险选择：

- 文案或微型视觉：目标状态、相邻状态、窄窗或边界状态。
- 交互：正常路径、失败或禁用路径、状态退出后的结果。
- 跨模块：受影响消费者、回归边界、恢复或重复执行风险。

## 必须让 Chat 看到的内容

1. **本轮决策问题**：用户会遇到什么，为什么现在处理。
2. **改动与未改动**：文件和行为摘要，以及明确非目标。
3. **可核验证据**：真实测试、日志、差异片段或附件。
4. **证据边界**：分别列出“已证明 / 合理推断 / 尚未验证”。
5. **审查问题**：要求 Chat 尝试推翻结论，而不是默认实施正确。

本地文件路径不是 Chat 能看到的证据。视觉结论必须附上实际前后截图，或明确标为“尚未完成视觉验证”；没有可见图片时，Chat 不得对构图、层级、重叠、颜色或可读性给出 PASS。代码结论应提供可读差异、关键片段或可访问文件，不能只列文件名。

## 推荐模板

```text
<控制器 render-review-run-binding 的完整原文（已包含起止标记）>

<项目>｜<阶段>｜正式评审 <与 STATE_REVIEW_ROUND 完全相同的数字>

本轮决策问题
- <一个问题及其用户影响>

改动与边界
- 已改：<行为与文件>
- 未改：<明确非目标>

可核验证据
- <测试、日志、差异或真实附件>

证据边界
- 已证明：<证据直接支持的结论>
- 合理推断：<尚未被直接观察但有依据的结论>
- 尚未验证：<缺失的设备、状态、截图或人工体验>

请独立审查
1. <最重要的反证问题>
2. <边界或回归问题>
3. <证据是否足以支持结论>

硬边界
- <不能扩展的产品范围>

因果范围
- 只评审本次请求提交前已经存在的证据。
- 不要求本次回复之后才可能发生的登记、释放、删除或续接作为本次 PASS 条件。

不要默认 Luna 的判断正确。请先寻找反例并区分事实、推断和缺证。
输出：PASS / REVISE / BLOCKED；最多 3 个实质发现；一个唯一下一步，并写明目标、完成条件和最小验证。
如果范围外问题足以推翻本轮结论，可以单列 1 个 blocker；否则不要扩需求。

回复最后必须追加且只追加一个模型建议区块。普通情况使用：

[SUPERLUNA_MODEL_ROUTE]
MODEL_ROUTE: MEDIUM
VERDICT: PASS / REVISE / BLOCKED
[/SUPERLUNA_MODEL_ROUTE]

只有证据满足模型策略时才可改为 HIGH_ONCE 或 TERRA_REQUEST。升级区块还必须包含 BLOCKER_ID、SIGNAL、EVIDENCE、SCOPE、EXIT_CRITERIA；TERRA_REQUEST 另须包含 HIGH_ATTEMPT。正文里出现“高”或“Terra”不构成升级建议。
```

标题可以不写轮次；如果写 `Round N` 或 `第 N 轮`，必须先通过
`validate-review-packet --state <state-file> --text-file <完整审阅包>`。工作过程自己的重试或迭代
只能写作 `工作迭代` / `Work iteration`，不得作为正式评审轮次发送。

## Chat 回复的最低质量

有效回复必须包含：明确结论、证据充分性判断、至少一次反证检查、剩余风险，以及一个可执行下一步。只有赞同、复述改动或泛泛建议的回复不进入自动实施，应显示“需要你决定”。

## 模型建议的权限边界

- Chat 只能建议，不能切换模型。
- 没有唯一且位于回复末尾的完整区块时，一律按 `MEDIUM`。
- `PASS` 不得建议升级。
- Luna High 最近 10 个有效开发步骤最多使用 2 次；Terra 最近 20 个有效开发步骤最多使用 1 次。上限是天花板，不是使用目标。
- `TERRA_REQUEST` 必须引用同一 blocker 的已完成 High 尝试；否则控制器拒绝。
- 任何 Terra 建议仍须能力确认、安全边界和用户明确确认，每次只允许一个动作。
