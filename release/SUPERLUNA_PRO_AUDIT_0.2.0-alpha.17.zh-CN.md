# SuperLuna 0.2.0-alpha.17 Pro 独立审核请求

## 审核目的

请对附件中的 SuperLuna 完整源码、测试、文档和发布证据做一次反例优先的独立审计，并给出可直接交给 **Grok Build** 执行的下一阶段开发指令。不要把测试通过、字段存在、命令名称或文档声明本身当成真实平台能力证明。

本次只请求审核和开发指导，不授权发布、部署、创建新 Chat、绕过 App 权限或扩大系统范围。

## 产品目标与不可改变的边界

SuperLuna 的目标是一个非技术用户也能理解的简单闭环：

```text
Luna 完成一轮实施
→ 向固定 ChatGPT 桌面 App Chat 提交结果与必要文件
→ 只在“等待 Chat”期间启用一次性门控检查
→ 读取同一请求对应的完整回复
→ 原实施任务继续修改
→ 再提交下一轮
```

用户只看到五种状态：正在开发、等待 Chat、正在按 Chat 意见修改、需要你决定、已完成。

固定边界：

- 项目只有一个写入者；固定 App Chat 是正式评审通道。
- 浏览器只可由用户明确选择为人工降级，同一轮不得双重提交。
- 旧固定周期 heartbeat 永久退役；开发和修改期间不得运行或排队检查。
- 过期检查不得读取 Chat、写项目、取得执行权、改变状态或输出提示。
- 系统不得假装已经自动切换 App 模型或推理等级。
- Luna 默认“中”；High / Terra 只是严格受控的例外，不是目标。

## alpha.17 的实际范围

alpha.16 的 Pro 复审指出：`verified` 容易被理解成平台已经自动确认模型执行。alpha.17 只收紧执行事实语义，不新增 App 模型控制能力：

- 版本 `0.2.0-alpha.17`，控制器 10，状态 schema 7，技能修订 `2026-08-04.40`。
- `verified` 记录必须同时具有 `execution_verification_type=manual_attested` 和 `verification_source=manual_confirmed`。
- `record-high-attempt` 仍只记录授权，不等同于实际执行。
- 旧 alpha.16 的 verified 记录迁移为人工证明，不包装成平台验证。
- `model-status`、doctor 和 audit 显示验证来源与类型。
- Terra 仍要求同一 blocker 的 High 人工证明事实。

## 必须主动攻击的反例

1. 旧状态迁移、手工构造状态、重复或重放 `verify-execution`，是否能绕过“授权不等于执行”。
2. 用户可见状态、doctor、audit、CLI 是否仍会把人工证明误述为平台自动验证或模型已切换。
3. Terra 建议、请求、确认、完成和失败恢复，是否都绑定同一个 blocker；是否有旁路或假执行事实。
4. Pro / High / Terra 配额、证据和恢复记录是否可能因重复事件、并发租约或旧状态迁移而被污染。
5. 等待检查到期后排队、主流程已离开等待、重复启动、旧 token 补跑、读取后再次到期，是否全部零副作用。
6. 同一请求与回复身份的一次性配对、网络不确定后的 reconcile、断点恢复和重复消费是否仍然安全。
7. 双 App 的主 App / 评审 App 角色隔离、固定 Chat ID、极高回读和实例关闭失效是否存在误绑定风险。
8. 102 项测试和 15 项自检中，哪些只是结构断言或模拟，哪些真正覆盖行为；指出“假绿”可能性。
9. 发布包、版本号、README、CHANGELOG、插件清单、控制器注册表、安装脚本和已安装技能之间是否一致。
10. 对公开 beta 的真实缺口是否被低估：当前发布报告只记录 3/10 个真实项目连续循环，Windows 完整闭环和 macOS 版本矩阵仍未完成。
